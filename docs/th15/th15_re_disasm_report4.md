## 1. 问题 1：`0x4E73F8` 章节号编码语义（正常游玩）

### 1.1 写入链（确认 + 补全指令层）

```
ECL 指令 opcode 0x20C（ins_524，参数 = 章节号）
  └→ 解释器 FUN_004291e0 case 0x43（≈0x42C7D0）
      └→ FUN_00432ec0(param)                    [th15.exe.c:35812]
          ├─ [StageCtrl + 0xB0] = param         // StageCtrl = 0x4E9A94
          └─ [StageCtrl + 0x90] |= 0x8000       // 置"章节切换"标志
  └→ 关卡控制器每帧 FUN_0043cc50                [th15.exe.c:41868, LAB 0x43D081]
      检测 [StageCtrl + 0x90] & 0x8000
      └→ FUN_0043dd30(&0x4E73F0, [StageCtrl+0xB0])   [0x43D0E5]
          └→ [0x4E73F0 + 8] = param  →  即 0x4E73F8
```

- **`0x4E73F8` = game_state + 8**，唯一写入点为 `FUN_0043dd30`（0x43DD30，`[EBX+8]=EAX`），全 exe 无其它直接写（`DAT_004e73f8` 全部为读引用）。
- `FUN_0043dd30` 在章节变化时同时维护重试计数（`+0x37C` 总重试、`+0x380+关*4` 每关、`+0x3A0` 当前段），即"进入新章节"事件。

### 1.2 是整局累计还是每关重置？→ **都不是；每关由 ECL 写死常量，跨关重复**

- 章节值**不是"每关递增"也不是"整局累计"**，而是**各关 ECL 脚本里写死的常量**（`ins_524(值)`）。
- **关键发现：章节值跨关不唯一、大量重复**（见 §2）：
  - 每关起始都是 **81**，每关结束都是 **41**；
  - 各关道中段用 0,1,2,3,4,5,6,7,8（小值，重复）；
  - 各关 boss 战用 43..68（重复）；
  - 道中 boss / EX 用 22,23,24,31,32,33（重复）。
- **推论：`0x4E73F8` 单独无法唯一标识"某关某段"，必须联合 `0x4E73F0`（关卡号）组成 `(关, 章节)` 键。** 开发组 §3 附代码只读 `0x4E73F8` 查表，**应改为同时读 `0x4E73F0` 再查 `(关, 章节)` 表**。

### 1.3 `0x2A/0x2B`、`0x16..0x28` 界限含义（修正前几轮猜测）

- 前几轮"正常游玩取值 0..0x2A"的观察**不完整**。ECL 章节值实际可达 **81**。
- 真实分区（`FUN_0043cc50` 比较 `0x43CEC2/0x43CFDB/0x43D01A/0x43D03B`，反汇编 `0x43D0B7`）：
  - **`< 0x2B`(43)**：普通段 / 非 boss 段分支；
  - **`> 0x2A`(42)**：另类处理（`th15.exe.c:41957, 42005, 42010`），对应 boss/边界；
  - **`0x16..0x28`(22..40)**：`FUN_0043ab70` 置"是否 boss 类段落"（`0x43D0B7~0x43D0D0`），= 道中 boss / EX 段。
- 结论：**道中普通段 = 0..21；道中 boss/EX = 22..40；关底 boss = 43..68；关起始 81 / 关结束 41。**

## 2. 问题 2：各关「章节号 → 段落」映射（从 ECL 提取）

### 2.1 章节指令 = ECL opcode `0x20C`（ins_524）

- 查表验证：解释器分派 `lookup[opcode − 0x12C]`（表 `0x42DE78`）中 **opcode `0x20C` → case `0x43`**（与已定案的 `0x200`→0x37、`0x202`→0x39 同一机制）。
- 参数 = `ins_524(章节值)`，值位于指令负载 opcode 起 `+12` 处的 4 字节 dword（经 `st03bs.decl:25 ins_524(43)` 与 `st03bs.ecl @0x378 = 0x2B` 交叉验证）。
- 章节指令同时出现在主关卡脚本、道中 boss（mbs）、关底 boss（bs）脚本中。

### 2.3 与开发组 `mChapterSetup` 的关系

- **不一致 / 需修正**：开发组假设"各关道中章数"与 `mChapterSetup`（ST1=2 ST2=3 ST3=3 ST4=3 ST5=4 ST6=4 EX=5）对应——但 **ECL 实际章节值不是按 1,2,3… 连续编号**，而是跳跃常量（81/41/0/1/2/3/4/5/6/7/8/22/31…）。**无法用"章节号 − 某偏移"算法映射到道中段序号。**
- **推荐落地**：直接建 `(关, 章节值) → 标签` 静态表（值域有限：道中 0-8、22、31，boss 43-68，起止 81/41），而非按 `mChapterSetup` 推章节号。

> 注：§2.2 序列为"全文件扫描"结果（含分支子函数），未对分支/跳转做执行序剥离。若需要**严格的主流程执行序**（哪些章节命令实际在正常游玩主线依次执行），可另行做 ECL 控制流分析。

## 3. 问题 3：miss/bomb 时点读取 `0x4E73F8` 的可靠性

- **可靠**。`FUN_0043cc50` 是关卡控制器每帧更新，与 miss/bomb（`FUN_00454a70` 玩家状态机，钩子 `0x456398`/`0x41497A`）**同帧执行**；章节切换在章节边界触发，章节进行中 `0x4E73F8` 恒定，不会读到相邻段落值。
- 读取表达式：`*(int*)RVA(0x4E73F8)`，或 `*(int*)(*(int*)RVA(0x4E9A94) + 0xB0)`（同值）。
- 无需额外挂"章节切换"指令点；若需更精确可在 `FUN_00432ec0`（0x42C7D0 区）或 `FUN_0043dd30`（0x43DD30）挂钩，但**不必要**。

## 4. 问题 4：是否有更细/更友好的道中位置字段

- **没有**"道中 N 段"的独立字符串/标题字段。HUD 章节显示即用 `0x4E73F8`。
- 旁证：`FUN_00426050`（敌人/boss 构造，0x26050）读 `0x4E73F8` 存入 `puVar6[0x15CD]`；boss 对象 `+0x114a` 亦存章节号（解释器 case 0x43）。
- 结论：`0x4E73F8`（或 `[StageCtrl+0xB0]`）即唯一来源，配合关卡号建表即可。

## 5. 推荐落地方案（对开发组）

```cpp
static std::string GetMidStageName()
{
    if (g_boss_ptr && (*(uint32_t*)(g_boss_ptr + 0x4060) & 0x800000))
        return {};                                  // boss 战 → 走既有阶段名路径
    int st = *(int*)RVA(0x4e73f0);                   // 关卡 1..7（7=EX）
    int ch = *(int*)RVA(0x4e73f8);                   // 章节（ECL ins_524 值）
    // 查表 (st, ch) → "道中N段"/"道中boss"/"关起始"/"关结束"；查不到保底记原始章节号
    auto it = kMidTable.find({st, ch});
    return it != kMidTable.end() ? it->second : ("ch" + std::to_string(ch));
}
```

- 表内容建议开发组基于 §2.2 各关序列 + 关内段落标题（HUD）实测校准后固化（因 ECL 值跳跃，不宜用算法推）。
- **重要**：读章节号必须同时读关卡号 `0x4E73F0`（章节值跨关重复），修正开发组 §3 附代码仅读 `0x4E73F8` 的写法。

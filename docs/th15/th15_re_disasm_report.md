## 1. Boss 当前阶段（最关键）

### 1.1 结论：boss 对象字段 `+0x4070` = 当前攻击序号

- **字段**：boss 对象（= ECL 解释器钩子命中时的 `EDI`）`+0x4070`，dword。
- **写入点**：ECL 指令 0x200（"set boss mode"）case 0x37 处理器，`0x42B987`：

  ```
  0042b92d  push 0x0                  ; ECL 参数索引 0
  0042b92f  mov ecx,edi
  0042b931  call 0x00430320           ; EAX = ECL 参数[0] = 新模式/攻击序号
  0042b936  push 0x0
  0042b938  mov esi,eax               ; <<<<< thprac 钩子（case512，2B）
  0042b93a  call 0x00425570
  0042b93f  test esi,esi
  0042b941  jns 0x0042b971            ; 新序号 >= 0 → 正常进入
  0042b943  test dword [edi+0x4060],0x800000
  0042b94d  jz  0x0042b962
  0042b94f  mov ecx,[edi+0x4070]      ; 旧序号
  0042b955  mov eax,[0x004e9a80]
  0042b95a  mov [eax+ecx*4+0x48],0x0  ; 清 ECL 数据槽
  0042b962  and dword [edi+0x4060],0xff7fffff   ; 清"攻击中"位
  0042b96c  jmp 0x0042dba7
  0042b971  push dword [edi+0x44b8]
  0042b977  or dword [edi+0x4060],0x800000      ; 置"攻击中"位
  0042b981  push esi
  0042b982  call 0x00425530
  0042b987  mov dword [edi+0x4070],esi           ; <<<<< boss+0x4070 = 当前攻击序号
  0042b98d  jmp 0x0042dba7
  ```

- **取值语义**：0 起 / 由 ECL 脚本指定（`param[0]`），战斗进行中为非负；**非 boss 战 / 战斗结束后保持上次遗留值**，不可直接用该字段判断"是否在 boss 战"。
- **配套战斗标志**：`[boss+0x4060]` 的 bit `0x800000` = "boss 攻击进行中"（case 0x37 正常路径置位；攻击结束/清场时清除）。bit `0x40000000` = "本次攻击已激活需收尾"。
- 同场另两个相关字段：`[boss+0x3F80] = 序号*7`（case 0x36 写入）、`[boss+0x3F74/3F78/3F7C]`（case 0x36 写入，疑似 HP/血量相关）。

### 1.2 boss 对象指针怎么拿（方案定型依据）

- **没有找到独立的"当前 boss 指针"全局量**。解释器 `FUN_004291e0` 的 `EDI` 来自其调用链（`FUN_004291d0` 是 EnemyInf 虚表槽 `0x4CC2E8` 的 thunk，`0x4291D6` 尾跳 `FUN_004291e0(param+0x120C)`），对象指针随敌人对象而来，不落地到固定全局。
- 因此方案选择：
  - **推荐（自维护）**：在 thprac 已有的 3 个 ECL 钩子回调里把 `pCtx->Edi` 缓存进静态变量 `g_boss_ptr`。这三个地址命中时 `EDI` 恒为同一个对象（解释器入口 `0x42921F: mov edi,ecx` 一次设置，全程不变），且 opcode 0x200/0x202 只有 boss 脚本会用到，所以缓存值就是当前 boss 对象。
  - miss/bomb 时读 `*(int*)(g_boss_ptr + 0x4070)`，并可用 `*(int*)(g_boss_ptr + 0x4060) & 0x800000` 判定是否在 boss 战中。
  - 与"读内存全局"方案对比：多一个缓存维护点，但地址链最短、无需猜测偏移，且与 thprac 现有钩子完全兼容。

### 1.3 `0x4E73F8`（章节号）在正常玩法的语义

- **是游戏状态结构 `0x4E73F0`（game_state）的 `+0x8` 字段**。写入点（已反编译确认）：

  ```c
  // FUN_0043cc50（关卡控制器每帧更新），当 [StageCtrl+0x90]&0x8000 有章节切换标志时：
  FUN_0043dd30(&DAT_004e73f0, *(int *)(StageCtrl + 0xb0));   // 0x4E73F0 作为 this，写入 this+8 = 0x4E73F8
  ```

  即 `FUN_0043cc50` 把 `[StageController(0x4E9A94)+0xB0]` 的章节号写入 `0x4E73F8`，随后 `0x4E73F8` 被 `FUN_0043cc50` 自身（`0x43CEC2/0x43CFDB/0x43D01A/0x43D03B`）与 `FUN_00451100`、`FUN_00451740`、`FUN_00426050` 等读取。
- **取值范围（正常游玩）**：0..0x2A（43）以内（`FUN_0043cc50` 中与 0x2A/0x2B 比较）；章节 0x16..0x28（22~40）被单独归类（`FUN_0043ab70` 参数按"是否在该区间"置 0/1），疑似 boss 战段落区间。
- **道中 / boss 战区分能力**：随"关内段落（章节）"变化——进入 boss 段时会变一次，但 **boss 段内每个非符/符卡之间不会变**。故它只能区分"道中 vs boss 战（段落级）"，**不能**区分"关底 boss 第 N 个攻击"。boss 段内攻击序号须用 §1.1 的 `[boss+0x4070]`。
- 练习模式下 thprac 用 `10000+关*100+章节` 编码直接写该地址，与正常游玩的小整数编码不同，勿混用。

### 1.4 是否存在"boss 战斗进行中"标志位

| 地址 | 语义 | 适用性 |
| --- | --- | --- |
| `[boss+0x4060]` bit `0x800000` | **boss 攻击进行中**（case 0x37 置位/清除） | 最直接，但需要 boss 指针 |
| `[0x4E9A80+0x18C]` | 活跃敌机 ECL 脚本计数（分配 +1 / 释放 −1） | 道中、boss 战都 >0，**非 boss 专属**；死亡/炸弹判定门槛（`0x557BA`、`FUN_00414a80`） |
| `[0x4E7794]` bit 组合 | 游戏模式/状态（bit `0x30`：`0x20`=关内进行；`0x300`：练习/符卡练习等） | 区分"是否在关卡中"，不区分道中/boss |

## 2. Boss 转阶段执行点（case 512 / 514）

### 2.1 定位与等价关系（已用二进制跳转表验证）

- ECL 解释器 = **`FUN_004291e0`**（巨型 switch，body `[[0x4291E0,0x42B82C],[0x42B830,0x42DBCB]]`）。分派：读 `[脚本指针+4]` 的 16 位 opcode → `opcode − 0x12C` → 查表 `0x42DE78` 得 case 号 → 跳转表 `0x42DBCC`。
- **实测表项**：
  - `lookup[0xD4]`（opcode `0x200`=512）= `0x37`，`jumptable[0x37] = 0x0042B92D`
  - `lookup[0xD6]`（opcode `0x202`=514）= `0x39`，`jumptable[0x39] = 0x0042C735`
- 因此 thprac 的两个钩子分别位于 **case 0x37**（`0x42B938`）与 **case 0x39**（`0x42C738`）分支内——与"set boss mode / SetNextPattern"注释吻合，**命名即 ECL opcode 值 512/514**。

### 2.2 hook 命中瞬间的寄存器/栈语义

**case512 钩子 `0x42B938`（覆盖 `mov esi,eax`，2B）**
| 寄存器 | 语义 |
| --- | --- |
| `EAX`/`ESI` | **新攻击序号** = `FUN_00430320(boss, 0)` 返回值（ECL 参数[0]，带符号） |
| `EDI` | boss 对象 |
| `[ESP+0x24]` | 当前 ECL 脚本指令指针（解释器栈局部） |
| 栈 `[ESP+0x1C]` | boss 对象备份（同 EDI） |

> 若新序号 < 0 表示"结束当前攻击"（清标志、清 ECL 槽）；≥0 表示进入新攻击，最终 `[EDI+0x4070]=序号`。**在 `0x42B938` 命中时新序号已装入 EAX，是捕获阶段的最佳点。**

**case514 钩子 `0x42C738`（覆盖 `mov [esp+0x2c],eax`，4B）**
```
0042c735  lea eax,[esi+0x20]
0042c738  mov [esp+0x2c],eax          ; <<<<< thprac 钩子
0042c73c  mov eax,[0x004e7794]        ; 游戏态
0042c741  and al,0x30
0042c743  cmp al,0x20                 ; ==0x20 且在 boss 攻击中 → BossDead 分支
0042c745  jnz 0x0042c791
0042c747  test dword [edi+0x4060],0x800000
0042c751  jz  0x0042c791
...
0042c791  push 0x2 ; (正常分支)
0042c795  call 0x00430320             ; EAX = ECL 参数[2] = 下一个攻击序号
...
0042c7d6  call 0x0042ff10             ; 挂接"下一个攻击"（SetNextPattern）
```
| 寄存器 | 语义 |
| --- | --- |
| `EAX` | `[ESI+0x20]`（对象子结构指针，仅作为 `FUN_0042ff10` 的第 4 参） |
| `EDI` | boss 对象 |
| `ESI` | 当前攻击数据区指针（`[ESI+0x20]` 是其子结构） |
| **新模式号** | 不在寄存器——在 ECL 参数 `[2]`，hook 之后才经 `FUN_00430320` 读入 |

> 结论：**若想在同一点拿"新阶段序号"，case512（0x42B938，EAX 立即可读）优于 case514（0x42C738，需再读 ECL 参数[2]）**。若两个钩子都保留，`0x42B938` 可用于记录，`0x42C738` 可用于区分"BossDead/换阶段"事件。

### 2.3 是否所有 boss 每次换攻击都走这两条路径

- **解释器层**：攻击切换只由这两条指令驱动（0x200 设置当前序号、0x202 切到下一攻击并处理 BossDead/BossEscape），除此之外的 case（0x30~0x40 区间）均为普通动作指令，不改变"当前攻击序号"。因此**道中 boss 与关底 boss 的每次换攻击必然经过 case 0x37 或 0x39**（符卡/非符皆然）。
- **"所有 boss 都执行一遍"的最终确认**属于 ECL 脚本层（§5），各 boss 脚本是否每条阶段切换都发 0x200/0x202 需按 `data/ECL/*.decl` 抽查；但从解释器结构看无其它切换通道。
- **例外/特殊**：EX 面与 ST6 特殊 boss 也走同一解释器（同一 exe 代码），无非另有入口；符卡被击破（BossDead 分支）会先清 `[EDI+0x4070]` 对应槽再进下一阶段，`[EDI+0x4070]` 始终为"当前有效阶段号"。

### 2.4 其它可挂接点

- `0x42C7E4`（case 0x39 尾部）：BossDead 后真正切换脚本（`FUN_00430000`），在此可见"下一阶段"参数；但已晚于 `0x42B938`。
- 死亡/换阶段共用 `FUN_0042ff10`（`0x42FF10`，BossDead/BossEscape 挂接器），若只关心"boss 换阶段"事件，可改挂它（`this`=脚本资源、`param_1`=当前阶段、`param_2`=下一阶段）。
- 显示符卡名的执行点在 `FUN_0042e160`（case 0x1D 附近调用于 `[ESP+0x2C]` 的子结构），可作旁证但不如 case 0x37 直接。

## 3. 游戏开始 / 结束判定

### 3.1 `0x43E6EE`（th15_game_start）触发时机

- 所在函数 `FUN_0043e6d0`，**每关开始都会调用**，不是"每局一次"：

  ```c
  // FUN_0043bff0（关卡开始流程，`0x43BFF0`）末尾：
  FUN_0043e6d0(0x4e73f0);     // 0x43E6EE 钩子在此函数内
  ```

  钩子点 `0x43E6EE` 实际写的是 `game_state+0x6C = 0x4E745C = 炸弹 = 3`（并初始化 power 等），即"本关初始状态"。
- `FUN_0043bff0` 同时在进入关卡时：`DAT_004e73e8=1.0f`、清零帧计数 `0x4E73FC/0x4E7400`、`DAT_004e75b8=0`（本关重试数）、按模式设残机（`0x4E7450`）、重设 `0x4E7794` 游戏态等。
- **结论**：它触发于"进入任意一关"（新开、续关、练习跳关、一关 clear 进下一关都触发）。作"新一局"边界时需配合 `0x4E73F0==1`（正常流程第一关）判定；若 thprac 想要的是"任何一次新关卡都另起一行"，用它即可。

### 3.2 一局结束的各路径

| 结束方式 | 执行链 | 关键地址 |
| --- | --- | --- |
| **残机耗尽 → GameOver/Continue** | PlayerInf 状态机 case2 发现 `0x4E7450<0` → `FUN_00451100`（GameOver/Continue 处理：设 stage 控制器状态、播 SE、显示 "Pause" 字幕） | 调用点 `0x454BD2` 附近；`FUN_00451100` 入口 `0x451100` |
| **通关（6面/EX clear）→ 结算** | 关末 → 下一关 `FUN_0043bff0`；最后一关结束后进入结算菜单（写 `0x4E73F0`/`0x4E7794` 的 `FUN_004515A0`、`FUN_004608D0`、`FUN_00451740` 等） | 结算函数族 `0x461xxx~0x46xxxx` |
| **游玩中退主菜单 / 暂停退出** | 玩家对象销毁：`FUN_00453300` 置 `0x4E9BB8=0`；stage 控制器状态变化 | 玩家销毁 `0x453365` |
| **统一可观察标志** | `PLAYER_PTR (0x4E9BB8)` 为 0 即"一局外"（创建于 `FUN_00453fd0`→`0x45404A`，销毁于 `FUN_00453300`→`0x453365`）；配合 `0x4E7794` 游戏态位 | `0x4E9BB8` |

> 建议落地：`0x4E9BB8==0` 作为"一局外"的落盘条件；`FUN_0043bff0`（`0x43E6EE` 钩子）作为"新一局/新关卡"另起一行的条件（可叠加 `0x4E73F0` 过滤）。

### 3.3 关键游戏状态全局（已确认）

| 地址 | 语义 |
| --- | --- |
| `0x4E73F0` | game_state 基址；+0 = 当前关卡（1~7，7=EX） |
| `0x4E73F8` | game_state+8 = 当前章节号（正常游玩 0..0x2A，练习模式 10000+编码） |
| `0x4E73FC`/`0x4E7400` | 帧计数（`FUN_0043cc50` 每帧 +1；进关清零） |
| `0x4E73E8` | float，进关/复活/GameOver 复位为 1.0f；ECL 指令可写（`0x42D768`）。非阶段号 |
| `0x4E7418` | game_state+0x28，ECL 数学用时间/相位值（-400..600 区间），非阶段号 |
| `0x4E7450`/`0x4E745C` | 残机 / 炸弹 |
| `0x4E75B8` | 本关重试数（进关清零）；每关重试数组 `0x4E7598 + 关*4` |
| `0x4E7794` | 游戏模式/状态位（bit`0x30`：`0x20`=关内进行；bit`0x300`：练习/符卡练习等） |
| `0x4E9A80` | ECL 管理器（+0x180 链表、+0x18C 活跃脚本计数、+0x48+序号*4 阶段数据槽） |
| `0x4E9A8C` | 会话对象（残机/炸弹显示源，`FUN_0043a850/0043a960`） |
| `0x4E9A94` | 关卡控制器 StageController（+0x90 标志、+0xB0 当前章节号、+0xB4 新/续关标记、+0xB8 章节帧计数） |
| `0x4E9BB8` | **PLAYER_PTR**（0=一局外） |

## 4. Miss / Bomb 执行点复核

### 4.1 两个钩子的函数与上下文

**miss 钩子 `0x456398`（5B，覆盖 `mov [0x4e7450],eax`）** — 函数 `FUN_00456370`（`0x456370~0x456537`）：
```
00456392  mov eax,[0x004e7450]
00456397  dec eax                       ; 残机-1
00456398  mov [0x004e7450],eax  <<<<< HOOK（命中时 EAX=残机-1）
0045639d  js 0x004563b1                 ; 残机<0 → 进入死亡收尾
0045639f  push dword [0x004e7454]       ; 否则正常结算
004563a5  mov ecx,[0x004e9a8c]
004563ab  push eax
004563ac  call 0x0043a850               ; 刷新残机显示
```
- 命中瞬间：`EAX=新残机数`，`EDI`=玩家对象（`0x4E9BB8`），**读取 `0x4E73F0`（关卡号）与该帧任何阶段状态均可靠**（纯数据读取，无时序竞争）。

**bomb 钩子 `0x41497A`（5B，覆盖 `mov [0x004e745c],eax`）** — 函数 `FUN_00414900`（`0x414900~0x4149DC`）：
```
00414950  ...（炸弹对象初始化）
0041495e  mov eax,[0x004e745c]
00414963  dec eax
00414964  jns 0x0041496a                ; 雷数 clamp 到 [0,8]
0041496a  ...
00414974  mov ecx,[0x004e9a8c]
0041497a  mov [0x004e745c],eax  <<<<< HOOK（命中时 EAX=clamp 后的新雷数）
0041497f  test ecx,ecx
00414981  jz 0x0041498f
00414983  push dword [0x004e7460]
00414989  push eax
0041498a  call 0x0043a960               ; 刷新炸弹显示
```
- 命中瞬间：`EAX=新雷数`（clamp[0,8] 后），`ESI`=炸弹对象，读 `0x4E73F0` 同样可靠。

### 4.2 掉命/扣雷的完整时序（决定"阶段号是否最新"）

```
FUN_00454a70（PlayerInf 每帧状态机）
 ├─ state1：炸键 && 雷>0 && FUN_00414a80()==1 → FUN_00414900（0x454B9F）→ 钩子0x41497A
 ├─ 受击判定 0x4557B1：需 [0x4E9A80+0x18C]!=0、无章节切换、[player+0x658]>=0x14、未死、非无敌
 │    └─ call 0x458DE0（死亡处理）→ call 0x452E80（置死亡倒计时）→ 死亡音效 → player 状态=4
 ├─ state4：bomb 键可在 0~7 帧内雷击取消（call FUN_00414900 + FUN_00456740）
 ├─ state4：[player+0x630] > 7 → FUN_00456370（0x454BBD）→ 钩子0x456398（残机-1）→ goto state2
 └─ state2：0x4E7450<0 → FUN_00451100（GameOver）；否则复活（雷回3、DAT_004e73e8=1.0f）
```

- **Boss 阶段号（`[boss+0x4070]`）由 ECL 解释器在攻击切换时更新，与 miss/bomb 相互独立**。掉命/扣雷瞬间读到的 `[boss+0x4070]` 就是"当时正在进行的攻击"（本帧内 boss 脚本不会因玩家掉命而改变阶段），**取值即为最新**。
- 唯一注意：若 thprac 走"缓存 `g_boss_ptr`"方案，需保证缓存与钩子执行同线程、且在 stage 切换（`FUN_0043bff0`）时清空，避免读到上一关残留 boss。

### 4.3 掉命路径上的"先行执行点"（Q4）

| 地址 | 说明 | 是否适合做记录点 |
| --- | --- | --- |
| `0x4557B1` | 受击判定（无敌/未死/无章节切换/有敌人脚本时） | 在"确认掉命"之前，含雷击取消窗口，会误记 |
| `0x458DE0` | 死亡处理入口（唯一调用者 `0x4557F5`） | 同上，早于确认 |
| `0x452E80` | 死亡状态设置（写死亡倒计时） | 同上 |
| `0x456398`（现状） | **残机扣减，仅当 0~7 帧雷击取消窗口过后才执行** | **最佳**：掉命已成定局 |

结论：`0x456398` 即"确认掉命"的正确点，无需前移；若希望记录"受击但被雷救回"的事件才需要改挂 `0x458DE0`/`0x452E80`。

## 5. ECL 脚本层面（可选调查，本文部分完成）

### 5.1 阶段推进的指令通道（解释器层已证）

- 唯一会改变"当前攻击序号"的指令：opcode `0x200`（写 `[boss+0x4070]`）与 `0x202`（切换下一攻击 / BossDead / BossEscape）。其余 opcode（case 0x0B~0xA9）均为动作/属性指令。
- 因此各 boss（道中 boss、关底 boss、EX、ST6 特殊 boss）的每次非符/符卡切换必然经过这两条路径之一。**具体各 boss 的阶段序列（每个阶段的序号编码）** 需读 `data/ECL/st0X*.ecl` + 解释器参数约定确认（ECL 参数经 `FUN_00430320` 从 `[脚本指针]` 处读取，0 起索引）。本报告未逐关核对，作为 follow-up。

### 5.2 章节类指令（th15_chapter_set）

- 钩子 `0x43DD58` 位于 `FUN_0043dd30`（章节写入函数），被 `FUN_0043cc50` 以 `FUN_0043dd30(&0x4E73F0, [StageController+0xB0])` 调用——即正常游玩下 `0x4E73F8` **不是由 ECL 章节指令直接写入**，而是由关卡控制器在章节切换时写入（ECL 章节指令触发的动作会走到 `FUN_0043cc50` 的 0x8000 标志分支，间接生效）。
- `FUN_0043dd30`/`FUN_0043dee0` 同时维护重试计数（game_state+0x37C 总重试、+0x380+关*4 每关重试、+0x3A0 当前段重试）。

## 6. 落地建议（对 thprac）

1. 新增 ECL 钩子侧缓存：在 `th15_lock_timer3`（`0x42B938`）、`th15_lock_timer2`（`0x42C738`）、`th15_bossmovedown`（`0x42B261`）任一回调中 `g_boss_ptr = pCtx->Edi;`（三个钩子 `EDI` 为同一对象，任选其一即可，建议用 bossmovedown，它与既有 boss 逻辑最贴）。
2. miss/bomb 回调中：
   - 关卡号：`*(int*)RVA(0x4e73f0)`
   - boss 阶段：`g_boss_ptr ? (int)*(uint*)(g_boss_ptr+0x4070) : -1`；是否 boss 战：`(*(uint*)(g_boss_ptr+0x4060) & 0x800000)`。
   - 一局边界：`FUN_0043bff0` 的 game_start 钩子（`0x43E6EE`）另起一行（可按 `0x4E73F0==1` 过滤"新局"）；`0x4E9BB8==0` 收尾落盘。
3. 若不想引入 `g_boss_ptr`，退而求其次：miss/bomb 时读 `[0x4E9A80+0x48 + pattern*4]` 需要先有 pattern，故不成立；仍以缓存方案为准。

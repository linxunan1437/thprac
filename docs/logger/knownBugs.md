## 2. 说明

**#1（th15 ST7）详述**

- 口径：CSV 是**路过式 checkpoint（latch）白名单**——运行期读「当前 ECL sub 名」，命中表内函数即置「当前段落」。
- 问题：`MainSub04` 在 thprac 的 warps 表里对应**两个**不同的记录名（`ST7 前半 #5` 与 `ST7 后半 #1`），但运行期两者是**同一个 sub**，白名单无法二选一。
- 现状：Csv 中两行都填了 `MainSub04`（机械规则所致），实际效果是「命中 `MainSub04` 时只会把段落置为后出现的那一行」。
- 修法（未做）：需 CSV schema 支持「同名入口 → 多记录名」的消歧（如加一列区分条件），或运行期结合额外状态（关卡进度 / 前一 sub）判段。
- 参考：`docs/logger/checkpoint_entry_backfill_workflow.md` §1（latch 口径）、§5（边界）。

**#2–#4（日志落盘）详述**

- 口径与实现见 `docs/logger/logger_impl_report.md`。三条都是**已知可接受**的边界，不影响主链路：
  - **#2**：事件记录的是「钩子触发时刻的当前段落」，而当前段落由每帧 `Update()` 维护，天然有一帧滞后。要在同一帧内消除需把 latch 提前到 tick 内，代价大于收益。
  - **#3**：定长数组是为了满足「热 hook 内零堆分配」（`feat/plogth15` 的崩溃前车之鉴）。溢出时**不静默**：JSON 里会带 `eventsDropped`。
  - **#4**：th18 无现成机体来源；若要补，需按 `docs/gametime/` 的探针流程新增逆向，属独立任务。

**#5（一局边界）详述**

- 现状：`Begin()` 在 `*_game_start` 钩子里**无条件**开新局（若上一局还开着，先把上一局转为待落盘）。
- 静态证据：该钩子所在例程把 score(`0x4A57B0`)、graze(`0x4A57C0`)、power(`0x4A57E4`) 归零、bomb 置 3 —— 若每关都跑，跨关分数会被清空，故语义上是「开新的一局」。但**未真机钉死**。
- 验证：真机 th16 练习从 ST1 打到 ST2，看月度文件里出现 1 行还是 2 行（`logger_impl_report.md` §7 验证项 3）。
- 若确认每关触发，修法（一行）：`Begin()` 里把「无条件开新局」改成「仅当上一帧不在局内（`!mWasInGame`）才开新局」，否则只做段落复位。

**#6–#7（单章节合并）详述**

- 口径与实现见 `docs/req_logger.md` 口径 11、`logger_impl_report.md` §3.1 / §5.1。两条都是**已知可接受**的边界：
  - **#6**：改写失败分两类 —— `GuardFailed`（打不开 / size 守卫不匹配）**一字节未动**，优雅退化成追加新行；`IoFailed`（`SetFilePointerEx`/`WriteFile`/`SetEndOfFile` 失败）则可能留下「旧行前半 + 新行后半」的撕裂行。只有磁盘满 / IO 错误能触发，此时用户本来就会先撞上别的问题。要根治需「写临时文件再原子替换」，对每 10–20s 一次的热路径不划算。
  - **#7**：基线放在 `GameSession` 的私有成员里，进程一退就没了。要跨进程必须**读回文件最后一行并解析**（`game` / `start` 日期 / `startCheckpoint` / `total` / `got` / 字节偏移），而 `req_logger.md` 口径 1 明确「不读回改写」——本次只开了「改自己刚写的那一行」这一个口子，不扩大到解析既有行。

**#13（th11 章节 sub 复用）详述**

- 口径：CSV 是**路过式 checkpoint（latch）白名单** —— 运行期读「当前 ECL sub 名」，命中表内函数即置「当前段落」，未命中 **no-op**（不回退 `main`）。
- 根因：th11 的白名单第 1 列按 **warp 落点**回填（`checkpoint_entry_backfill_workflow.md` §1），而 th11 的 `main` 是**纯容器**、段落子脚本大量经 `async`（opcode `0x0F`）起独立线程；同一个 `MainSubNN` 被 `main` 在**不同阶段复用**（增援波、二次演出）。latch 一旦**再次命中同名 sub**，就把段落置回**第一次调用**对应的记录名。
- 站点（离线核对，见上表）：ST1 的 `MainSub03`/`MainSub07`、ST4 的 `MainSub03`/`04`/`06`、ST5 的 `MainSub00`。ST7 的第二次 `MainSub03` 与首次同值，**无可见变化**（故不计入）。
- 与 **#1（th15 ST7）同类**：都是「白名单单值列装不下『一个入口 → 多记录名』」。th11 的形态更广 —— 不是两行冲突，而是**同一行被二次触发**。
- 修法（未做）：① 给这些行改记 **`sub名+0x偏移`**（运行期**偏移命中优先**）—— 骨架已在 th10（18 行）/ th13（1 行）落地，th11 侧缺的是**偏移值**，须从 `.ecl` 二进制反推二次调用点的指令偏移；② 或重定这些行的 warp 落点。
- 参考：`docs/logger/checkpoint_entry_backfill_workflow.md` §1（latch 口径）、`docs/th11/th11_monitor_impl_report.md`。

**#14（th10 `ST4 后半 #2` 不显示）详述**

- 现象：真机（2026-10-20）`ST4 后半 #1`（`MainSub5`）正常，`#2`（`MainSub6L`）不显示。
- 已核实的静态事实（**不是**原因，只是排除项）：
  - `MainSub6L` 在 `stage04.decl:2463` **存在**，名字与 CSV 第 1 列**一致**（⇒ 排除「decl 名与白名单名不一致」）。
  - `:2388 @MainSub6L() async;` 与 `:2390 @MainSub6R() async;` **无条件顺序执行**，中间只隔 `+30:` 的等待 ⇒ **L/R 不是 A/B 路线分支**（⇒ 排除「走了另一条路线所以没命中」）。
  - 同文件 `MainSub8L`/`MainSub8R`（`:2667`/`:2721`）同构，且在 `:2653`–`:2663` 被**三次交替**调用。
- 调用形态差异（可能是关键）：`MainSub5` 由 `:2262 @MainSub5();` **同步**进入，`MainSub6L` 由 `async` 派生 ⇒ 两者**线程并存**。监控是「每帧遍历宿主链 × 线程链 + last-hit-wins」，两个线程同时命中不同白名单键时的裁决顺序（宿主链 / 线程链的遍历次序）**尚未验证**。
- 与 **#13（th11 同名 sub 复用）**、**#1（th15 ST7 同名入口）**的区别：本条是**纯名行、且名字唯一**，不是「一入口多记录名」问题。
- 处置：**用户 2026-10-20 定案 —— 先记录不修**，待后续完整测试（把 th10 各关各段一次性跑完）时统一解决，届时按上面三条待查方向定位。

**#15（th10 `spellFlag` 的 card→card 同帧跳变）详述**

- 口径：口径 15 的 `spellFlag` 是**每帧一次**采样符卡对象 flags 的 bit0 的 `1→0` 下降沿。**各作 flags 偏移互不相同**（不可跨作外推）：th10 `obj+0x378C`、th11 `obj+0x8E0`、th12 / th13 `obj+0x7C`、th14 `obj+0x7C`、th16 `obj+0x78`。
- 根因：th10 有 **8 处「卡→卡」直接转移**（`setNext` 目标直接是下一张 `BossCardN`），下一张卡所在 sub 的首条指令就是 `spellEnd()`（结算上一张），紧跟 `spell(...)`（声明下一张），**中间没有任何 `wait`** ⇒ 同一帧内 bit0 `1→0→1` 回到 1；帧末采样看到的是 1 ⇒ **下降沿被吞掉**。
- 对照（逐作枚举，非外推）：th11 的 11 处 card→card 全部带 `+60:` / `wait(60)`–`wait(180)`；th12 / th13 静态枚举为 **0 处**（每张卡后必接一个非符 sub，其首条指令即 `spellEnd()`，bit0 在整个非符期保持 0）⇒ **只有 th10 受影响**。
- 影响方向：**假阳性**（该抑制 `interrupt` 时没抑制 ⇒ 多记一条），与 **#12**（`spellFlag` 滞留窗口 ⇒ 假阴性）方向相反、机理同源 —— 都是「一帧一采样 vs 真实沿」。
- 缓解（现有，已足够）：这些转移点本身就是 checkpoint 切换点，段落变化会 `--mSpellFlag`（下限 0）；关底最后一张卡到 `BossDead` 要 `+60:` 才 `spellEnd()`，不受影响。
- 修法（未做）：把采样挪进 ECL tick 内逐指令（代价大，且与「热 hook 内零堆分配」的设计冲突），或在 `spellEnd` 处挂点（**新增 hook**，违反本次「零新 hook」约束）。
- 参考：`docs/th10/th10_monitor_impl_report.md` §9；`docs/logger/logger_impl_report.md` §4.4.2；对照 **#12**。
